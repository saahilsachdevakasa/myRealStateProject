# Manual Setup Steps

This file tracks one-time Setup-UI steps that cannot (or should not) be captured in `force-app/` metadata. Whenever the SDO is refreshed or a new org is created, these steps must be reproduced manually **before** running `./scripts/deploy.sh`.

## Why this exists

Some Salesforce features can only be enabled through the Setup UI (or via `sf org create scratch` with specific definition files, which we don't use on SDO). Capturing these steps here makes SDO refreshes reproducible.

## Protocol

Every time Claude Code (or Sahil) configures something via Setup UI that is not in source metadata:

1. Add an entry below under the appropriate section.
2. Include: the Setup path, exact values chosen, and the epic ID where the step first became necessary.
3. If the step can be eliminated by adding metadata to source, do that instead and remove the entry.

#### E04 — Demo user first-login (temp passwords)

**Security note:** Temp passwords below are one-time values generated by the SDO's password policy at seed time. They are intentionally weak (demo-org practice) and will be reset by each user on first login. Do not copy this file or its passwords to any production-adjacent repo. The SDO itself is disposable — on refresh, re-seed and a new set of temp passwords is generated.

**When needed:** post-deploy of E04, after `sf apex run --file scripts/seed-demo-users.apex --target-org re-crm-sdo` completes.

**Seed outcome (2026-04-22 run):** 7 demo users created, each assigned the correct RECRM_* role (6 of 7) and persona permission set. Username pattern `<handle>@recrm-demo.invalid` — `.invalid` per RFC 2606 is DNS-level non-deliverable, so welcome/notification emails bounce safely.

**First-login flow:**
1. Navigate to the SDO login URL (`sf org open --target-org re-crm-sdo` for the System Admin; for demo users, use the same org instance URL).
2. Enter username (`<handle>@recrm-demo.invalid`) and the temp password from the table above.
3. Salesforce will require a password change on first login. Set a new password and complete the security question setup.
4. User is now live — confirm by checking the App Launcher shows only the tabs their permission set grants.

**SDO password policy note:** the SDO's org-level policy allows short temp passwords (as seen above, 5–7 chars). This is a demo-org default — production would have longer minimums and complexity rules. Do not propose tightening the SDO policy; the demo flow depends on these short passwords being accepted.

**Why not in source:** Salesforce does not allow `User` records as deployable metadata — they must be created via API/UI/Apex. The Apex seed script (`scripts/seed-demo-users.apex`) handles creation idempotently; this doc captures the one-time output (passwords) that only exists at seed time.

**Re-seed after SDO refresh:**
```bash
# 1. Deactivate any prior demo users (idempotent no-op on a truly fresh org):
sf apex run --file scripts/delete-demo-users.apex --target-org re-crm-sdo

# 2. Deploy all metadata (E01-E04 inclusive):
./scripts/deploy.sh re-crm-sdo --skip-validate

# 3. Re-seed demo users (emits a fresh set of temp passwords to stdout):
sf apex run --file scripts/seed-demo-users.apex --target-org re-crm-sdo
```
After re-seed, update this table with the new temp passwords.
